# Shelf 使い方マニュアル

SKYNovel/BlueSNovel製ゲームのランチャー「Shelf」の使い方・開発者向けの案内。

## プレイヤー向け

（第2段階・生成ツール実装時に書く）

- Shelfの基本操作（起動・更新・購入先を開く）
- カードの表示が「確認が必要」「製品版を確認できません」になったときの意味

## 開発者向け

### Shelfに自分のゲームを登録する

`shelf/gen/`（生成ツール）を起動する（`npm run gen:dev`）。

1. 「サークル情報」タブでサークル名・公式サイト・報告先・メールを入力する。初回起動時に
   マニフェスト署名用の鍵（ed25519）が自動生成され、`~/.shelf-gen/signing-key.json` に
   保存される。**この鍵を失うと、既に配布済みのランチャーは新しいマニフェストを一切
   検証できなくなる（全ランチャーの作り直しが必要）。バックアップを取ること。**
2. 「作品管理」タブで「＋ 作品を追加」し、ゲームのプロジェクトフォルダを選ぶ。
   `package.json`から作品名・識別子（appSlug）が自動で入り、`doc_crypto/prj`等の存在から
   `crypto:true`かどうかも自動判定される。
   - `crypto:true`の場合、`doc/prj`配下に`setting.sn`が1つだけ・プロジェクト直下に
     `pass.json`があれば、「setting.snのファイル名」欄に推定値が自動で入る
     （下の「購入者チェックが使えない場合」参照）。この条件を満たさない場合や、
     過去出荷インストーラーからの抽出に失敗する場合は手入力が必要。`crypto:false`なら
     既定値（`setting.sn`）のままでよい。
3. 過去出荷インストーラー（.exe/.dmg）を「選択して追加」し、購入者チェック用のチェックサムを
   抽出する。mac(.dmg)はそのまま抽出できる。Win(.exe、NSIS)の抽出には7-Zip
   （`brew install p7zip`等）が要る。
4. 最新版インストーラーを選び、「R2へアップロード」する（先に「ホスティング」タブで
   Cloudflare R2の認証情報を保存しておくこと）。
5. 「ランチャーを生成」を押すと、mac向け(universal dmg)・win向け(事前ビルド済みstubがあれば)の
   配布物と、署名付きマニフェストが組み立てられる。
6. 「ホスティング」タブの「マニフェストをアップロード」でマニフェストを公開する。

Win向けの配布物は、Windows実機で`shelf/app`をビルドし、
`shelf/gen/prebuilt/x86_64-pc-windows-msvc/shelf.exe`に配置しておく必要がある
（blues-sync経由の受け渡し運用。クロスコンパイルはできない）。

### SKYNovelの自動更新パッチ（[update_check]）を公開する

プロジェクトフォルダに `build/package/update/_index.json` があると、作品カードに「SKYNovel自動更新パッチ」欄が出る。
欄は、公開までの鎖を順番に並べた手順表示になっている。

1. 元（doc/prj）
2. 暗号化出力（doc_crypto/prj）
3. main.sn の update_check（url）
4. mac バンドル（dmg）／5. win バンドル（exe）
6. update 一式（_index.json）
7. R2 公開

各工程に ✓（最新）・⚠（上流より古い可能性）・✗（確定的な不一致）・–（対象外/確認できない）と更新時刻が付き、
最初の問題のある工程が「次はここ」として色付けされ、上部に「次にやること」が出る。上から順に直していけばよい。
「再チェック」で状態を取り直す。

- **このツールから実行できる操作**: 工程3の「url を設定」（main.sn の url 値だけを書き換え、cond等は保つ）と、工程7の「R2へアップロード」だけ。
  暗号化・バンドル・配布形式の生成は SKYNovel 側の作業で、欄にはやることだけを示す。
- **urlを設定したら**: 今ある `build/package/update` は古い `main.sn` をバンドルしたものなので、工程4・5・6が ⚠ になる。
  再バンドルして dmg・パッチ一式を作り直してから、アップロードする。
- **判定の根拠**: 工程間は更新時刻の比較（推定）。版（package.json と _index.json）、ファイルの有無・サイズ、
  R2 の `_index.json` との版・sha512・cn の違いは確定的な不一致として扱う。内容そのものの差分は見ない。
  `path.json`・隠しファイルは更新時刻の比較から除く。
- **アップロード**: `build/package/update/` の全ファイルを `patch/<appSlug>/<階層>/` へ上げる（`_index.json` は最後）。
  階層内の旧ファイルは削除し、削除したキー名をステータスに出す。工程1〜6に警告があるときは、公開前に確認ダイアログが出る。
  公開階層は main.sn に既にある R2 公開URL配下を維持する（配布済みアプリが見に行く場所なので変えない）。

### 購入者チェックが使えない場合

Shelfは、インストール済みのゲームが過去の正規購入者のものであることを、`setting.sn`
（暗号化済みファイル。鍵は一切使わず、既知のチェックサムとの一致だけで判定する）で確かめる。
次のような場合、この自動チェックが機能しない。

- **過去出荷ビルドに体験版チェック機構（`setting.sn`）自体が実装されていない。** テンプレート
  更新前の古いビルドでは、このファイルがasar内に存在しない場合がある。生成ツール側で
  インストーラー本体のチェックサムによるフォールバック（②）を用意すること。
- **`const.体験版`がプロジェクト側で改名・削除されている。** テンプレート標準の慣習に
  依存しているため、変更するとチェックの土台ごと成立しなくなる。
- **電子透かし（`&const.体験版`）自体が平文アクセスできない構成（`crypto:true`）。** この場合、
  体験版の混入は自動検出できない。生成時に警告を出すだけに留める。
- **`crypto:true`プロジェクトの`setting.sn`ファイル名（basename）は`uuidv5(relPath, pass)`
  で求まる値で、実データで一致を確認済み（2026-11-17）。生成ツールは`doc/prj`配下に
  `setting.sn`が1つだけ見つかり、かつプロジェクト直下に`pass.json`がある場合のみ自動計算する。**
  `doc/prj`に`setting.sn`が複数（プロジェクトによって`theme/`・`script/`等、置き場所が違う）
  ある、または`pass.json`が無い場合は自動計算されず、手入力が必要（過去出荷インストーラーの
  抽出に失敗する場合も同様。実際のapp.asarを確認して正しい値を入力すること）。

これらに当てはまる場合、Shelfのカードは「確認が必要」と表示され、購入者に当時の
インストーラー本体を選んでもらうことで判定する（②フォールバック）。

### マニフェストの署名

生成ツールは ed25519 鍵でマニフェストに署名し、ランチャーは埋め込み済みの公開鍵で検証する
（自動インストールは取得物を実行するため、マニフェストの完全性検証は省略できない）。

鍵は生成ツールの初回起動時に自動生成され、`~/.shelf-gen/signing-key.json`（0600権限）に
保存される。この鍵は一度作ったランチャーに公開鍵が焼き込まれるため、失うと既配布分が
全て検証不能になる重要な秘密——リポジトリの外（ホームディレクトリ）に置くのはそのため。
生成ツールのUIに「作り直す」操作は無い（事故防止）。バックアップは利用者自身の責任で行うこと。
